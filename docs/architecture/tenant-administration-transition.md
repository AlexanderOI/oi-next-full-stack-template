# Tenant administration: preserve data, converge on full Admin

**TENANT-ADMIN-001 is a read-only transition contract, not an implementation or an executed migration.** The product has one full-access organization **Admin** role (not exactly one administrator identity) and protected **Member**; no product Owner or cross-tenant sysadmin. Reuse `/admin/roles` and `/admin/users`, but convert every server read and write before exposing them as tenant administration.

Authority: `odd/tasks/tenant-administration.md` and `AGENTS.md`. This contract supersedes the reset/no-backfill, distinct Owner/limited Admin, and product platform-administration assumptions in `docs/architecture/multi-organization.md`. Its other tenant, restriction, invitation, and lifecycle invariants remain applicable. **No database reset, migration apply, bootstrap, backfill, grant script, or live DB operation is authorized here.** All data-shape evidence below is from source; deployed schema, row counts, and browser behavior are unverified.

## Compatibility and canonical authority

The following mapping is the reviewed target contract; its code and backfill remain **proposals until verified** against fixtures and an explicitly authorized deployed inventory.

| Existing state                                                                           | Target interpretation / preservation rule                                                                                                                                                                                                                                          |
| ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Valid protected organization Owner assignment                                            | Compatibility reader recognizes it as full Admin **in that membership's organization only**. Proposed backfill adds `system:organization:admin` without deleting the Owner assignment or definition. Owner becomes a dormant compatibility alias, never a selectable product role. |
| Valid protected organization Admin assignment                                            | Same ID becomes full Admin, including the five formerly excluded permissions. This is an intentional tenant-local grant expansion, requiring rollout review; it is not a cosmetic rename.                                                                                          |
| Both Owner and Admin                                                                     | One effective Admin principal; preserve provenance and avoid duplicate assignments.                                                                                                                                                                                                |
| Protected Member / valid custom role                                                     | Preserve existing assignments and tenant-local grants. Only Admin and Member remain product protected choices; custom roles cannot acquire platform or protected security permissions.                                                                                             |
| Legacy Owner invitation role ID                                                          | Validate the same tenant and current invitation policy, then resolve to Admin at acceptance. Proposed pending-reference normalization must not invalidate tokens, alter expiry/status, or create memberships. Preserve terminal invitation history.                                |
| `member.role` says owner/admin but canonical assignment is absent, foreign, or malformed | Deny; never infer or backfill privilege from a string alone. Report for reviewed repair, not automatic promotion.                                                                                                                                                                  |
| Platform role/assignment                                                                 | Preserve rows, IDs, links, and provenance. Platform **administrative** grants become dormant for product access; never convert them into memberships or tenant Admin. Existing own-profile grants remain distinct global identity behavior, not sysadmin.                          |

`membershipRole` plus validated organization role/permission scope is the **sole product grant authority**. `member.role` is a Better Auth lifecycle field, not an independent permission store. Current source uses owner/admin projections in signup/transfer but safe `member` in invitation acceptance; therefore an assumed universal equality rule would reject valid existing states. The target safe projection is `member` for product-owned lifecycle operations with stock endpoints still blocked. Compatibility must explicitly accept verified legacy projections, deny unexplained combinations, and normalize projections atomically with canonical writes. Do not expose provider admin/owner endpoints to implement full Admin.

Full Admin receives all organization-scoped catalog permissions, including deletion, administrator handoff (legacy `organization.ownership.transfer` key may remain internally), restriction creation, and allowlist administration. It receives no platform grants. Signup creates Admin only in its personal organization; retries recognize both verified legacy Owner and target Admin onboarding states without deleting established data.

## Authorization and continuity gates

- Authenticate an enabled global identity; resolve current session organization and its active membership on every protected request. For slug routes, require session/URL agreement. `/admin` has no slug: derive the organization from the session, require explicit selection when absent, and bind mutation input to the observed organization so a stale tab cannot silently mutate the newly selected tenant.
- Build snapshots/cache keys with organization and membership IDs. Never reuse a platform or previous-tenant snapshot after switching.
- Every role, membership, user, invitation, audit, count, and assignment query includes validated tenant predicates. User IDs must resolve through membership in that tenant; shared identities do not expose other memberships or grants. Protected role IDs must match scope/protection; custom role IDs must belong to the same organization. Reject foreign IDs without existence disclosure.
- Recheck actor state, target scope, role validity, and continuity inside serializable transactions or equivalent locks. Audit actor membership and tenant; revalidate affected paths after commit. UI hiding is not authorization.
- Every surviving organization retains at least one **distinct active, globally enabled canonical Admin membership**, counting valid Owner aliases during compatibility. Custom-role holders are not substitutes for protected Admin continuity. Demotion, assignment replacement, suspension, removal, leave, and handoff must enforce post-transaction continuity, including simultaneous attempts and global identity disabling across all affected organizations.
- Handoff grants Admin to a different enabled active same-tenant membership before optional source demotion, atomically. Organization deletion is an explicitly confirmed operation, not an exception allowing a surviving organization to have no Admin. Preserve existing restriction/allowlist, final-membership deletion, and post-commit session cleanup policies; the transition itself deletes no identity, organization, or session.

2. **Code first:** test and deploy compatibility readers, full-Admin policy, continuity checks, signup retry support, invitation alias handling, and tenant-bound lifecycle writers before changing stored grants. Review TENANT-ADMIN-002 independently. Keep old broad admin experiences gated during cutover; mixed old/new writer versions must not race.
3. **Convert reused pages:** complete tenant role and user reads/actions/components (003/004), including permission catalog filtering and membership-local access semantics. Global identity consequences of existing lifecycle rules remain transactional, never an unrestricted platform user toggle.
4. **Bootstrap proposal:** revise bootstrap to synchronize full organization Admin without erasing legacy Owner or platform definitions/assignments or resetting custom grants. Separate definition synchronization from assignment backfill; test repeat runs and prevent old bootstrap from downgrading Admin. Existing platform Member/profile setup is not an admin promotion. Generate schema migrations only if a verified need exists; never apply them in code verification.
5. **Backfill proposal:** under a separately approved writer pause/lock plan, add Admin only to verified canonical Owner memberships, using the membership/role unique key; retain legacy rows and record exactly which assignments were newly inserted. Normalize agreed lifecycle projections and pending invitation references with before-images and conditional updates. Recheck continuity and scope per batch; inconsistent rows halt the batch, not trigger guessed repairs.
6. **Retire product platform administration (005):** only after tenant pages/actions pass isolation tests, remove platform admin navigation and product authorization paths, including direct Server Action invocation. Retain assignments dormant. Quarantine the platform grant CLI from product recovery; no automatic recovery promotion. Component responsibility-folder moves (006) are separate structural work, not migration prerequisites.
7. **Postflight (007):** reconcile aggregate counts and manifest deltas, verify tenant isolation and continuity, then reopen writers through a separately approved rollout. Browser/DB verification must be recorded as performed or skipped, never inferred from unit tests.

### Idempotency, interruption, and rollback

Assignment inserts use `(membership_id, role_id)` uniqueness and retain original actor provenance; retries must not overwrite existing grants or duplicate audit success. Conditional projection/reference updates and a versioned per-batch manifest distinguish already-converted rows from inconsistent ones. Each batch is atomic; interrupted execution resumes only after read-only reconciliation.

Do not roll back to old platform-facing administration or run old bootstrap against expanded grants. Safe default is to gate affected administration and retain data while investigating. A data reversal is a separately reviewed conditional procedure: remove only manifest-proven inserted assignments, restore only unchanged manifest-owned before-images, and preserve last Admin continuity and subsequent legitimate writes. Former limited Admin privilege expansion cannot be blindly downgraded after users rely on it. Backups are disaster recovery evidence, not authorization for a reset or destructive restore.
